# View Engine 职责收敛与生产质量重构设计

状态：用户已确认书面设计，当前按配套实施计划执行与验收。

基线：`f632de3f`。范围：`packages/view-engine` 及受公共接口影响的宿主、Storybook、示例、技能与双语文档。记录视图是本次交付对象，分析视图不在本次实现范围。

## 1. 目标与约束

- 保留已确认的记录视图产品行为，提升职责清晰度、内聚性、可维护性，减少跨模块共享状态和重复逻辑。
- 允许调整公共 API 与保存配置结构，同步迁移仓库内全部接入，不维护尚未发布接口的旧兼容层。
- 继续保存可序列化的组件属性；组件提供纯编译能力，Wow 查询表达式不承担编辑状态恢复职责。
- 复用 Fetcher 生态、现有 UI 和表格能力。新增依赖必须有可验证的净收益，不预设引入状态机或通用流程框架。
- 不削弱权限、CAS、未知写入结果核对、请求身份、取消与重入、可访问性、性能等已确认约束。
- 九项未提交高度布局改动单独保留，不将它们作为本次重构基线或静默覆盖；本次需要修改同一文件时按变更块隔离。
- 自动合并保持暂停；设计确认、实现、独立审查和验收完成后，再恢复对精确提交的 CI/connector 合并检查。

## 2. 现状与问题依据

本包有 138 个 TypeScript/TSX 源码文件。初步静态导入扫描均可从公共入口到达，因此当前没有仅凭“文件未引用”就可删除的文件名单；符号、分支、重复转换仍需分别核验。

已确认的结构性问题及审查重点：

1. `FilterDraftNode` 同时承载顶层 `value/values/lowerBound/...` 和 `props`；`filterConfigurationState` 依据组件名称展开或收拢这些属性。编辑和持久化存在两套树结构及隐含优先级。
2. `useFilterPanelState` 同时兼容查询表达式、受控草稿、已应用草稿与本地模式/基线，需要多条 Effect 同步路径。宿主与 React 容易重复承担状态协调。
3. 运行时近期已把写入恢复收拢到 `InstanceWork`，并修复完成通知与查询归属。后续重构必须维护这些不变量，而不是重新分散状态。
4. `recordModel` 混合契约、列布局和格式化实现；内部聚合导出与实际职责需要重新核查。
5. 高覆盖率不能证明操作序列正确。现有恢复/重入回归是保留资产，测试组织应围绕行为及不变量，而不是让每个内部函数都拥有独立镜像测试。

上列文件规模用于定位审查入口，不作为拆文件或认定代码有缺陷的充分依据。

## 3. 采用的路线

采用按职责渐进重构：先收敛组件配置和状态所有权，再迁移 React 与宿主接入，最后删除失去用途的内部结构和兼容分支。

保留 `ViewHost` 的服务门面及 headless / React / styles 三个发布入口。不开启全量重写，不把记录视图提前抽象成分析视图框架，不要求迁移到状态机库。

中间步骤可以使用短期迁移代码，但最终候选不保留两套公共协议、废弃接口别名或双格式运行路径。每一步先建立行为证据再删除旧实现。

## 4. 配置与筛选组件树

### 4.1 唯一配置表示

保留 `FilterConfiguration`（模式与根节点）和 `FilterComponentConfig`（组件引用、操作符、字段绑定、props、子节点）作为唯一可序列化树。

- 内置组件和自定义组件均通过 `props` 读写编辑属性。
- 移除 `FilterDraftNode` 中顶层值字段与 `props` 的双轨表示，迁移后删除相应公共类型和往返转换接口。
- 组件引用在新建节点时解析并写入配置；定义中的编辑器配置仅作为新建默认值。已保存节点使用其明确引用，不依赖隐式恢复猜测。
- 可序列化的未完成输入留在组件属性中；焦点、选区、弹层开关等瞬时 UI 状态留在组件内。非序列化缓冲的有效性通过现有有效性通报机制影响查询资格。
- 清空属性与删除节点保持不同语义；已应用筛选标签的清除将对应值设为未设置，并按既有交互立即查询。

### 4.2 三个状态快照

同一种配置结构用于三种有明确用途的快照，不把它们合并：

| 快照       | 所有者与用途                                                           |
| ---------- | ---------------------------------------------------------------------- |
| 编辑草稿   | 引擎会话，或独立 FilterPanel 的受控调用方/本地状态；反映尚未应用的编辑 |
| 已应用配置 | 查询会话；与当前结果对应，保留未设置组件和显示属性                     |
| 已保存配置 | 实例基线；用于保存差异与撤销                                           |

编译表达式是已应用配置的派生查询值。查询是否待应用与视图是否待保存仍分别计算；仅改变组件显示属性、但不改变查询语义时，按现有行为更新配置差异，不强制产生无意义的请求。

### 4.3 API 收敛方向

- `FilterPanel` 的 `value/onChange` 以 `FilterConfiguration` 为输入输出；非受控入口使用 `defaultValue`，两种方式共用同一编辑流程，不同时维护互相回写的受控和本地草稿。
- 可提供 `appliedValue` 标识已应用配置；独立面板在成功应用后维护本地已应用基线。
- `onApply` 返回本次配置与编译表达式，允许异步完成；结果确认不得覆盖随后产生的新编辑。
- 模式来自配置，不再作为第二份独立受控模式源。
- 引擎草稿命令接收同一配置树；应用命令从当前草稿编译，不接收调用方另传的查询表达式作为第二个真相来源。
- 配置协议本身的结构、字段/操作符上下文规则与组件编译职责分别清晰，但使用同一套上下文规则；不在结构校验中调用第三方编译器。
- 不提供查询表达式反推组件树的公共 API；现有只用于示例和 fixtures 初始化的表达式构造改为组件配置构造。编译输出校验可以使用内部解析结构，但它不能成为第二套编辑树或持久化协议。

具体类型声明在实施计划中列出逐项替换表，并保证没有未处理的仓库调用方。

## 5. 运行时职责

| 单元           | 负责                                                | 不负责                     |
| -------------- | --------------------------------------------------- | -------------------------- |
| 配置与规则     | JSON 契约、字段能力、结构与上下文校验、纯配置变换   | 网络、React、订阅生命周期  |
| 编辑状态       | 草稿/应用/保存差异、列与排序编辑、查询资格          | 宿主持久化、组件焦点与弹层 |
| 查询           | 分页/游标、结果与汇总、请求身份、取消、自动读取归属 | 保存视图、决定权限策略     |
| 实例写入与恢复 | 写入互斥、原请求身份、版本与回执、未知结果核对      | 渲染、业务数据保存         |
| 会话存储       | 不可变快照、派生状态、发布订阅                      | 重新实现编译或宿主服务     |
| ViewEngine     | 对外命令与各职责的组合                              | 成为所有业务规则的实现文件 |

内部文件按上述职责组织。纯类型契约与格式化/布局实现分离；不以新增层数或减少单文件行数作为目标。

每实例写入/重载/恢复上下文由单一单元管理，其他单元不直接修改其 Map。查询控制权单独管理，因为读取和持久写入的生命周期不同。状态完成、控制权释放、通知和后续读取使用明确的一致顺序。

## 6. React、组件与宿主

- RecordView 消费引擎快照并发出命令，不再维护第二套可持久化编辑状态。
- 独立 FilterPanel 保留独立使用能力，通过同一配置树和纯变换复用规则；不依赖 ViewEngine。
- 组件可拥有瞬时交互状态；外部配置替换、切换视图、禁用和卸载时，旧回调不能写回新的编辑会话。
- 保留全局、表格/批量、行、筛选器、单元格五个扩展点，以及内置组件注册方式。统一引用与错误展示规则，避免重复的适配层。
- 表格布局和格式化继续优先使用已安装的 TanStack 与格式化能力；不能为内部重组改变固定列、宽度、汇总或选择的已确认交互。
- ViewHost 保留 definition、instance、preference、permission 与业务 source 的职责分离。数据权限、持久化事务、CAS 和幂等回执仍由服务实现保证。
- LocalStorageViewHost 作为可执行服务契约验证宿主。只在职责和测试边界确实需要时分离存储读写、事务和服务操作，不为了对应接口数量机械拆类。

## 7. 错误、取消与恢复不变量

实施与审查必须逐条验证：

1. 每次发布的选中键均属于当前结果；取消回调或同步订阅中的新查询不能留下旧选择。
2. 对外发布操作完成时，内部操作资格与快照一致；随后发起的新操作不被旧 finally 解锁或覆盖。
3. 较新查询、取消、导航和重载意图优先于旧操作的自动后续读取。
4. 无效宿主定义/配置在准入边界失败；未注册或运行失败的组件按明确的组件错误处理，不伪装为可查询状态。
5. 未知写入结果不会被当作失败重建新身份；原创建 requestId/body 与版本化删除核对语义保持。
6. 原视图不再可见时仍可核对创建，但不复活无权限源、不保留其业务行。
7. 权威 scope/revision、较新的独立副本编辑和已确认删除不被旧回执覆盖。
8. 单页查询、所有汇总、保存与导航错误分别归属正确位置，恢复动作不重放无关写入。
9. 完整加载、作用域变化和 dispose 使旧操作失效，并释放请求、订阅和运行时上下文。
10. 权限在操作执行时重新核查；系统视图不能删除或改名，当前用户排序不改变公共内容。

## 8. 死代码与依赖决策

死代码审查覆盖模块可达性、符号使用、分支可达性、运行时注册、公共导出与文档示例。公共导出仅无内部引用不等于死代码。

每个删除项记录：原职责、调用证据、替代位置或删除理由、保护行为的验证。保留必要的输入防御和恢复分支，不因低频或覆盖率低而删除。

依赖决策顺序：现有包/API、原生平台与标准库、已安装库，最后才评估新库。对候选记录替代的代码、包体/运行时/类型影响、取消与 SSR/无 DOM 核心兼容性、维护成本和测试结果。默认不新增依赖；只有能够保持上述不变量且净减少复杂度的方案才纳入实施计划。新增依赖遵循 workspace catalog，不让核心入口引入 React/DOM。

## 9. 接入与保存数据迁移

- 同一交付批次更新包导出、内置/自定义筛选器、RecordView、LocalStorage/开发 HTTP 宿主、fixtures、Storybook play、示例、技能参考与双语文档。
- 已存组件配置若因协议调整不再有效，开发存储使用新的格式标识/命名空间，旧数据明确提示重置；不静默猜测并丢弃属性，不保留双协议服务实现。
- 格式没有变化的保存数据应继续通过重新实例化宿主与引擎恢复，不能借重构无故清空。
- 不删除用户本地开发数据作为构建步骤；重置由开发页面明确操作。
- 尚未发布的 view-engine 接口允许一次性调整；若影响其他已发布 Fetcher 包的公共契约，需单独列明并遵循仓库版本策略。

## 10. 分阶段交付与验收

1. 建立当前调用/导出/状态归属清单，记录待清理项与行为基线。
2. 收敛筛选配置树，迁移全部编辑、编译、恢复和接入路径，再删除旧树和兼容转换。
3. 收敛运行时及 React 所有权，保留并扩展操作序列回归。
4. 完成职责重组、已证实冗余清理和依赖净收益评估。
5. 独立审查最终组合变化，并对精确候选执行交付验证。

验收不是一个覆盖率数字：

- 当前产品能力和五类扩展点完整保留；全部公共示例与类型检查通过。
- 单测覆盖关键行为和上述不变量；操作序列包含同步通知、取消、成功/失败、导航、重载与 dispose 的交错。
- 普通与 React Compiler 模式、Storybook 交互、包归档/无 DOM 核心、LocalStorage/HTTP 端到端恢复通过。
- 三浏览器生产场景覆盖明暗主题、1440/390px、键盘与焦点、错误/加载和 20 次挂载释放。
- 性能仍采用 100 行、30 列、100 筛选字段、10 次热样本、p95 不超过 1000ms 的现有门槛；不缩规模、不放宽预算、不用重复运行碰运气。
- 新发现的可访问性问题必须处理；已有经过记录的上游例外明确列出，不宣称未经验证的读屏器认证。
- 受影响构建、lint、格式、双语文档生成/检查/构建通过；提交前 `pnpm test:unit` 通过。
- 精确最终 HEAD 的 CI、Codecov、Codacy 及 connector 审查通过后才能按已有授权 squash 合并。

最终交付附接口迁移清单、删除清单、依赖决定、验证证据及剩余限制。不以文件更少、测试更多或代码行数单独宣称生产级质量。

## 11. 设计自审

- 本次仅记录视图，未混入分析视图新能力。
- 唯一组件树与三种用途快照不矛盾；表达式只作为编译结果。
- 允许接口调整不等于允许丢失数据或弱化恢复契约。
- 独立面板与引擎接入分别有唯一状态所有者，不要求两者相互依赖。
- 库选择有明确准入条件，未将选库决定预留为阻塞项。
- 清理以证据为依据；文档没有预先承诺删除尚未证实的代码。
