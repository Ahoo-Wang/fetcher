# AnalysisView 下一阶段契约输入

日期：2026-09-09。状态：下一阶段设计输入；本次不新增分析运行时或公开 API。当前已交付的数据视图继续使用 `kind: 'record'`。

## 用户任务与首期顺序

分析视图服务于“定义统计口径、比较结果、进入相关明细”。先完成维度/指标配置、可恢复实例与聚合结果表，再接指标卡、柱状图、折线图。图表消费同一份聚合结果；不在浏览器重新解释业务统计，也不把截取的分组行加总成全局总额。

开始实现前必须确定四件事：字段的聚合能力、保存的组件配置、编译出的结果 schema、展示绑定。先用真实 `AggregationQuery` 与结果行验证这些契约，再选择图表组件。没有这些输入时不抽象通用查询引擎或选择图表依赖。

## 已有能力与正确复用边界

| 已有能力                                             | 下一阶段用途                                 | 不能直接继承的记录语义                                                                         |
| ---------------------------------------------------- | -------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `FilterConfiguration`、过滤器注册、纯编译/清空函数   | 保存原始组件属性，恢复编辑器，编译运行时筛选 | 不从 `FilterExpression` 反向猜测 UI 属性                                                       |
| `ViewInstanceMetadata`、个人/公共/系统分类           | 实例身份、标题、归属、版本与用户展示偏好     | `ViewInstance` 目前只是 `RecordViewInstance`，尚不是多形态 union                               |
| `ViewHost.definition/instance/preference/permission` | 沿用服务职责和持久化/权限/CAS/幂等语义       | `load` 返回的当前 `ViewDefinition` 必填 `rowKey`；`resolveSource` 当前限定 `RecordQuerySource` |
| `ViewEngine` 中已验证的取消、只读快照、核对规则      | 作为独立分析生命周期的行为契约和测试参考     | `RecordSession` 的分页、记录选择、页内汇总、行操作不属于分析会话                               |
| shadcn/Base UI 基础控件、全局时区、数值/日期格式化   | 默认主题、交互、一致的格式和可访问性         | 记录列宽/固定设置不能决定维度或指标含义                                                        |
| `readRecordValue` 的自有属性点路径                   | 源记录字段绑定                               | 聚合结果按服务返回的别名读取，不把别名任意解释成源记录导航路径                                 |

**演进规则：** 先为 analysis 建立独立的配置和结果类型，再评估把确实相同的身份/服务契约移出 `record`。当前记录 API 保持可用；不能通过给记录属性大量加 `?`，让不完整对象同时冒充两类视图。是否扩展公开 union 与宿主数据源返回类型，由下一阶段的完整 schema 设计决定。

## 复用 Fetcher/Wow 查询能力

以当前公开 `@ahoo-wang/fetcher-wow` 为依据：

- `AggregationQuery`：`filter?`、`elements?`、`groupBy?`、非空 `metrics`、`sort?`、`limit?`。
- 分组：`TERMS`、`HISTOGRAM`、`DATE_HISTOGRAM`；日期分桶显式传递全局时区。
- 指标：`COUNT`、`NUMERIC`、`ANY`；数值函数为 `SUM/AVG/MIN/MAX`，表达式支持字段、常量及二元运算。
- `QueryApi.aggregate(query, attributes?, abortController?)` 已返回结果行数组；可直接由宿主桥接。`aggregateStream` 已存在，但首期不因此引入流式分析状态机。
- 使用现有 `aggregation` 构造器；不在 view-engine 重新定义一套传输 DSL、客户端或请求取消机制。

能力存在不等于所有业务字段都允许使用：定义必须声明可用维度、指标、函数、粒度和必要限制，编译器按定义校验。宿主负责真实字段权限和服务器查询执行。

## 保存内容与编译产物

保存的是维度/指标/展示组件的稳定 ID、注册名称、JSON 选项、字段绑定和原始属性；每个维度/指标还需要稳定的输出别名。显示名称与别名分离：改名不能改变表达式或打断图表绑定。

运行时编译产生两份彼此一致的输出：

1. `AggregationQuery`：给已有 Wow 聚合接口执行。
2. 结果 schema：别名、业务名称、值类型、空值语义、格式、维度/指标角色，以及展示所需的分组绑定。

下一阶段需要像现有过滤器一样将渲染与纯编译放在同一注册能力中；它可以独立用于无 React 的校验、保存与恢复。未知注册或无效属性明确阻断执行，原配置保留供修复。不要另外维护一份会漂移的 UI 配置与手写查询。

## 结果与展示约束

- 先校验结果行对象、预期别名和值类型；缺失别名是契约错误，不以零代替。
- `null`、零、空结果各有独立含义。无分组指标结果和有分组空集的预期形状分别定义，不能套用“所有汇总必须一行”的记录规则。
- 聚合结果不是业务记录，不强制使用业务 `rowKey`。若展示需要键，按完整分组元组建立稳定键，并保留字符串/数字/null 的类型区别。
- 图表横轴、系列与指标都绑定结果别名；每个查询维度必须有明确绑定，不能把不同分组误合成一个点。
- `limit` 表示服务返回规模限制；当前接口是行数组，没有 total/truncated 元数据。界面必须说明已设置的上限，不能据返回行数宣称“全部分组”。首期不提供无法证明正确的全局合计或分组分页。
- 指标卡要求无分组，切换展示时对不满足条件的配置明确反馈，不静默删除维度。
- 下钻使用已应用筛选与完整分组值共同定义范围，由宿主明确提供入口。没有宿主能力时不渲染无效按钮；不自动继承记录批处理/行操作。

## 下一阶段验收样例

| 场景                               | 必须证明                                           |
| ---------------------------------- | -------------------------------------------------- |
| 无分组 COUNT + SUM                 | 一份查询、稳定别名、零/null 区别、正确指标卡绑定   |
| 状态分组 + SUM                     | 组值与显示名称分离，聚合表/柱状图一致              |
| 本地时区日期分桶                   | 日期粒度、DST 边界、序列排序与筛选口径一致         |
| 两个维度 + 一个指标                | 完整组元组身份，不丢维度、不误合并图表点           |
| 用户改显示名称后保存重开           | 别名和查询不变，组件配置完整恢复                   |
| 迟到响应、失败、取消、权限变化     | 保留已应用结果与编辑草稿，拒绝过期回包，局部可恢复 |
| 结果缺少别名、重复分组键、非法数值 | 明确契约错误，不展示貌似有效的统计                 |
| 有限条分组与下钻                   | 明示上限和精确明细范围，不伪造全局总数             |

这些样例是下一阶段方案的入口，不表示分析能力已在本次实现或通过验收。
