# View Engine 第一阶段：错误边界与通用排序库化

日期：2026-09-13

设计基线：`main` / `022f1e69e33160b11e9431f00f1fee46b6b90c89`

状态：设计已获用户确认；按两份实施计划在当前会话顺序执行。

## 1. 目标与决策

用成熟的通用机制降低自维护代码量，同时保持查询、保存、权限和配置语义。第一阶段包含两个可以独立验收的交付单元：错误边界、通用列表排序。两者都通过后才宣布第一阶段完成；某一项未满足验收条件，不阻止另一项单独交付。

采用局部库化方案。仅在内部去重仍需维护输入传感器与错误边界状态；全面替换状态管理、校验与调度则会同时改变多个核心契约。后一方案不属于本阶段。

本阶段保留 `react-grid-layout` 负责 Dashboard 网格几何和缩放。Zod、Immer、XState、p-queue、fast-check 的引入，以及 DashboardRuntime 的职责拆分，分别属于后续评估，不捆绑到本次迁移。

## 3. 错误边界设计

### 3.1 迁移清单

源码目前有 7 处 `getDerivedStateFromError`。全部改用库提供的 `ErrorBoundary`，保留业务 fallback；不增加另一套自维护捕获/复位状态机。

| 现有边界                  | 迁移后职责                                     | 恢复身份                                                      |
| ------------------------- | ---------------------------------------------- | ------------------------------------------------------------- |
| `RecordRendererBoundary`  | 展示单元格、卡片字段、操作或区域的局部错误     | 保留当前 resetKey 各元素的 `Object.is` 语义，映射为 resetKeys |
| `ChartBoundary`           | 图表失败时保留下方数据表入口                   | 保留实例、结果与 presentation 的现有恢复身份                  |
| `AnalysisEditorBoundary`  | 编辑器渲染失败和手动重试                       | 保留编辑器所属组件的挂载与切换边界                            |
| `EditorBoundary`          | 筛选扩展失败后切换内置编辑器，通知所属编辑会话 | editor、session、operator、mode                               |
| `TransformEditorBoundary` | 转换器失败时阻止有效性误报，允许重试           | 保留转换器名称和上级面板/筛选/编辑世代的 key                  |
| `DashboardPanelBoundary`  | 单面板降级和重试                               | runtime identity、引用实例和 reference version                |
| `DashboardLayoutBoundary` | 布局模块重试、简洁布局、焦点和可用性通知       | runtime identity；显式重试创建新的 lazy 资源                  |

优先直接组合库组件；保留有业务意义的轻量命名组件，不创建一套重新包装全部第三方 props 的通用接口。

### 3.2 错误、恢复与数据边界

- 异常仍在最小渲染子树内隔离。单元格失败不移除整张表，单面板失败不移除仪表盘导航，布局失败仍可查看数据和保存配置。
- `onError` 通知所属编辑器或面板。普通异步查询、写入、事件处理异常继续进入现有错误通道，不统一改为抛给渲染边界。
- 库的 `onReset` 表示请求重试，不表示子树已经成功渲染。编辑器恢复通知必须在对应子树成功提交后发生，避免“仍然渲染失败，但会话被提前标记有效”的窗口。
- 编辑器恢复不得覆盖其自身报告的无效输入；只清理属于该边界、该编辑世代的渲染错误。
- 保留 `EditorSession` 与 `TransformEditorSession` 的已提交 owner、generation 和卸载保护。这两者是扩展回调生命周期控制，不是错误边界。
- 使用库 resetKeys 的逐元素比较，不以数组容器每次新建作为重试条件；也不以每次查询通知作为重置条件。
- 布局重试必须重新创建 `React.lazy` 资源，同时重置错误边界；不通过重建 ViewEngine 或 DashboardRuntime 取得表面上的恢复。
- 保留重试按钮、错误提示与键盘焦点恢复。验证重复失败后再次成功，以及取消重试/卸载后的晚到通知。

## 4. 通用排序设计

### 4.1 覆盖范围

现有 `useListOrder.ts` 为 164 行，复用于记录列、记录排序条件、卡片字段和分析维度/指标；`ViewManagerGroup.tsx` 为 183 行，并另有原生拖拽落点实现。行数包含注释和业务代码，只作为对照基线，不能宣称全部可删除。

迁移这五类排序入口，包括 `RecordColumnSettings`、`RecordSortSettings`、`RecordCardSettings`、`AnalysisEditor`、`ViewManagerGroup` 及其行组件。Dashboard 的 `DashboardGrid` 和 `dashboardLayout` 不改用 dnd-kit。

### 4.2 内部职责分工

建立一个内部列表排序组合层，直接使用新版 provider 和 sortable hook：

- 列表层负责传感器配置、中文操作说明、操作生命周期、权限/身份失效以及一次最终提交。
- 项目层负责现有 DOM 节点和手柄的 refs、可拖动状态、可视反馈；不强制增加 DOM 层，也不接管输入框或业务表单。
- 业务调用方继续持有唯一的配置/列表状态，提供稳定 ID、可移动规则和提交回调。不得复制一份长期存在的业务列表到交互层。
- 现有 `useListOrder` 的 HTML DragEvent 接口和 ViewManager 的重复落点代码移除；迁移所有内部调用方，不保留旧机制作为兼容层。

列排序保留固定区域和锁定列规则；视图管理保留个人/共享分组及持久化权限；分析编辑保留移除无效输出排序等联动规则。拖拽库不负责这些规则。

### 4.3 一次拖拽的数据流

1. 开始时记录当前操作身份、owner、按顺序排列的稳定 ID。列表不能以数组下标作为项目身份。
2. 库负责拖动预览、碰撞检测和临时排序；hover 不调用业务配置更新或持久化。
3. 利用项目接受规则以及 `onDragOver` 拒绝非法预览；不能允许视觉上跨越被禁止的固定区域，直到松手才提示失败。
4. 库的 optimistic sorting 会改变 source 的当前 index，target 也可能变成 source。提交根据 sortable source 的初始/最终位置计算候选重排，不套用旧 API 的 active/over 算法。
5. 最终提交重新校验操作身份、当前权限、owner、ID 顺序、源项目和业务可移动规则。初始 index 必须与所捕获的 source ID 一致。
6. 通过校验后，使用调用方的最新项目对象构造新顺序，并只调用一次业务更新。配置编辑不自动查询；视图管理仍经现有异步排序写入入口持久化。

### 4.4 并发更新与取消

新版库有 DOM optimistic sorting，因此不能照搬“拖拽期间暂停外部数据更新”的示例：权限与业务更新必须及时生效。

- owner、编辑世代、项目 ID 顺序、分组约束或可编辑权限变化时，取消当前手势并使操作 token 永久失效。随后采用最新权威列表。
- 项目标题等不影响排序资格和顺序的更新可以继续展示；最终移动最新对象，避免以旧对象覆盖内容编辑。
- 当前拖拽项被移除、排序对话框关闭、所属视图切换或组件卸载时，晚到的 drag-end 不得提交。
- 取消只清理库的临时反馈并恢复与当前受控状态一致的 DOM，不回写开始时的完整对象快照。
- 项目顺序变化时可重挂载轻量排序区域以结束 DOM 排序生命周期；不得重挂载引擎或恢复旧配置。普通内容更新不因此重挂载。
- ViewManager 持久化失败时继续使用现有错误与忙碌处理；只有写入成功才播报成功。不得留下与引擎实际顺序不一致的视觉顺序。

### 4.5 输入与可访问性

- 鼠标与触摸使用 PointerSensor；拖拽仅从可聚焦手柄开始。保持表单点击、文本选择和正常页面滚动。
- 默认采用库的按输入类型激活策略，防止轻点按钮或滑动页面误触拖拽。若浏览器验证出现误触，再通过 PointerSensor 按 pointerType 配置鼠标位移和触摸延迟阈值，并记录调整依据。
- 保留现有“手柄上方向键一步移动”快捷方式；水平列表增加左右键。一步移动复用与最终拖拽相同的业务提交函数。
- 支持 Space/Enter 拾起、方向键移动、Space/Enter 放下、Escape 取消。拾起状态下方向键完全交给库，不能同时触发一步移动和传感器移动。
- 说明、位置播报和取消播报使用中文。手动方向键移动与库拖拽各有单一播报源，避免重复朗读。
- 禁用手柄必须真实阻止开始/提交操作；权限恢复不得复活已经取消的手势。
- 排序后焦点保持在原项目手柄；项目已不存在时使用当前列表的相邻手柄或现有调用方 fallback。尊重 reduced-motion。

## 5. 对抗性验收

| 场景                                         | 必须成立的结果                                     |
| -------------------------------------------- | -------------------------------------------------- |
| 同一渲染器连续抛错、重试后仍抛错             | fallback 持续可用，没有无限重试或重复查询          |
| 修改 resetKeys 数组容器，但各元素不变        | 不触发恢复或重建业务会话                           |
| 已失败的旧编辑器回调在新编辑器提交后执行     | 不修改新会话内容或有效性                           |
| 布局 chunk 被真实阻断，重试先失败后成功      | 简洁布局和保存可用；新 lazy 资源恢复布局；焦点有效 |
| 拖动列越过固定区或锁定区                     | 无非法视觉预览，无配置变更                         |
| 拖动过程中移除源项目、重排列表、撤权后再恢复 | 手势作废，晚到结束事件无副作用                     |
| 拖动期间编辑项目标题                         | 成功重排保留最新标题；取消不覆盖编辑               |
| 同一页面包含多个相同项目 ID 的独立列表       | 每个 provider 隔离，不跨列表误移动                 |
| 管理视图排序服务失败或返回前界面关闭         | 错误可见，最终顺序正确，焦点和旧回调安全           |
| 键盘普通移动、拾起移动、取消连续操作         | 每次只有预期的一次提交，焦点和播报一致             |
| StrictMode、并发未提交渲染、卸载和再次挂载   | 无残留全局监听、无旧操作复活、无重复副作用         |

## 6. 收益与交付门槛

两项分别记录改动前后的自维护生产代码行数（排除空行、注释、测试、文档、生成代码），但计入新增适配组件、调用方改动和保留业务包装。每项必须净减少生产代码；不能用移动文件或删除必要保护制造收益。

结构验收要求：7 处自维护错误捕获状态机归零；通用排序不再维护 HTML5 拖拽落点/边界检测，也不存在两套排序手势实现。编辑器生命周期类保留，不作为失败指标。

测试与构建验收：

- 复用并扩展错误边界、扩展编辑器生命周期、列排序、视图管理排序和布局加载测试；源码与 React Compiler 产物均执行。
- 新增或更新 Storybook 实际浏览器交互，覆盖触摸模拟、键盘、滚动容器、弹窗、取消与撤权。触摸模拟不等于真实设备验收。
- 执行受影响包构建、类型、lint、格式与根 `pnpm test:unit`；提交前全量单测必须通过。
- 执行发布包验证，确认 core 导入图无 React/拖拽依赖泄漏，所有公开导出和示例继续有效。
- 分别记录核心入口和 React 消费入口的构建/gzip 体积。新功能依赖允许有可解释的增量，但必须列出准确增量、加载路径和所有传递依赖；不使用 npm 解包体积代替消费端体积。
- 受影响的实际交互使用同一 fixture、浏览器和机器比较；重放现有性能预算，不以库官方 benchmark 推导项目收益。
- 对外行为说明同步 Storybook 和中英文 wiki。若涉及公开 API，同步 skill API 参考；本设计目标是不改变公开 API。

如果适配代码抵消了删除收益、需要保留双实现、出现无法解释的性能退化，或需要删除现有业务保护才能迁移，该交付单元不通过，回到设计决策而不是继续叠加包装。
