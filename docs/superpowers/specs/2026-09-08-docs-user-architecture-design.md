# Fetcher 文档重构：使用者任务与架构决策

状态：实现、独立审查与本地验收完成；用户已授权提交并创建 PR。

## 1. 目标与范围

将文档组织中心从包与公开符号清单，转为两条阅读路径：使用者完成接入任务，架构师判断适用范围和集成责任。二者共享准确的 API 参考。

继续使用 VitePress、现有品牌资源和 Mermaid 交互。重构内容结构、首页、导航、参考页组织及示例验证，不修改 SDK API，不新增 workspace 包或外部依赖。不保留旧文档兼容层、迁移页、旧章节索引或重定向。

本设计替代上一轮站点设计中的内容组织方式。页面数量、源码行数和符号数量不作为文档质量目标。已有正确的 API 事实和验证用例可复用，旧页面结构不作为保留约束。

## 2. 两类读者的完成标准

| 读者       | 要完成的事                 | 文档应交付的结果                                   |
| ---------- | -------------------------- | -------------------------------------------------- |
| 首次使用者 | 从准备环境到成功运行       | 完整安装、文件位置、命令、预期输出和下一步         |
| 应用开发者 | 完成一次具体集成           | 可运行示例、所需前提、失败处理、资源清理及扩展入口 |
| 架构师     | 判断是否采用、采用哪些能力 | 依赖与运行边界、责任划分、组合方式、约束和采用成本 |
| 已有使用者 | 查询明确 API 行为          | 参数、默认值、结果、错误、生命周期与可定位符号     |

通用 TypeScript/React 用法先独立成立，Wow、CoSec 和远端 Viewer 作为有明确服务端契约的集成能力。架构内容解释当前实现，不承诺库尚未提供的缓存、重试、隔离或一致性保证。

| 路径             | 负责回答的问题                | 主要章节                                                                   |

## 4. 开始使用与首页

首页按以下顺序组织：

1. 一句话定义 Fetcher，说明其基于原生 Fetch 的位置。
2. 两个主要动作：开始接入、评估架构。
3. 一个展示核心调用的短示例；完整错误与环境设置留在可直接进入的教程中。
4. 按需求展示 HTTP、服务/流、React/数据视图三类入口，明确附加能力的前提。

首页不重复首次请求页的整段代码，不展示完整包清单或符号数量。源码证据、贡献命令和实现限制不混入首屏价值介绍。

开始使用的页面职责：

- `start/index.md`：从现有项目条件选择起点，明确纯 HTTP 与 React/Viewer 的不同前提。
- `start/installation.md`：提供可直接执行的安装方案和环境要求，不要求读者先跳到 package.json 才知道需要安装什么。区分消费者与仓库开发工具链。
- `start/first-request.md`：给出文件位置、完整代码、运行命令、固定预期结果；先建立一次成功调用，再引入必要的失败处理与类型边界。
- `start/first-view.md`：渲染有真实行列的数据视图，说明组件入口选择。最小示例必须展示 View/Viewer 的价值，不以通用状态 Hook 代替组件示例。
- `start/next-steps.md`：根据下一项应用任务进入指南；不要求先通读包目录。

## 5. 开发指南

指南按任务组织，每篇交代输入、环境、实际步骤、结果验证、失败处理和相关参考。完整流程只维护一份；架构与参考页链接它，不复制同一长例子。

| 指南组                 | 页面任务                                                                                  |
| ---------------------- | ----------------------------------------------------------------------------------------- |
| `guides/http/`         | 配置共享客户端；构造 URL/头/体；选择结果；处理 HTTP/传输/解析失败；取消与超时；扩展拦截器 |
| `guides/services/`     | 声明服务方法；从实际 OpenAPI 输入生成并使用客户端                                         |
| `guides/streaming/`    | 读取 SSE；处理终止/取消/无效数据；集成当前包支持的 Chat 流                                |
| `guides/react/`        | 显式请求；条件驱动查询；防抖；展示加载/错误；正确管理取消和卸载                           |
| `guides/viewer/`       | 渲染本地数据；连接分页/排序；加入过滤；保存视图；按后端条件选择远端集成                   |
| `guides/integrations/` | Wow 命令查询；CoSec 认证刷新；存储与事件协作                                              |

每组入口列出任务与前提，而非直接落到该组第一篇内部机制。任务标题使用“做什么”，API 名称保留为查阅线索。专业术语第一次使用时给出简短定义。

## 6. 架构与选型

架构页以决策问题为标题或开篇问题，给出选择依据、责任边界和代价；图表表达真实依赖或调用关系，明确图的含义。

| 页面                                    | 必须回答                                                                                                          |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `architecture/index.md`                 | 哪些问题适合 Fetcher？何时只用核心包？附加包要求哪些应用或服务端条件？                                            |
| `architecture/package-boundaries.md`    | 包的依赖方向是什么？哪些是类型/构建时工具，哪些参与运行时？peer 依赖与可选业务能力有何区别？                      |
| `architecture/runtime-support.md`       | 浏览器、Node 和 React 环境分别需要什么？SSR 中共享实例与状态的责任是什么？                                        |
| `architecture/request-lifecycle.md`     | 请求怎样经过 exchange、拦截器、传输、错误处理与结果提取？每个阶段在哪里结束？                                     |
| `architecture/state-and-resources.md`   | 客户端、Hook、Viewer、存储及总线分别拥有哪些状态？谁创建、取消、清理或持久化？                                    |
| `architecture/failure-model.md`         | HTTP、网络、解析、流与业务失败怎样区分？取消影响哪一层？哪些重试/缓存策略需要应用自行提供？                       |
| `architecture/integration-decisions.md` | 直接调用、装饰器与生成客户端怎样选择？View、Viewer 与 FetcherViewer 怎样选择？引入 Wow/CoSec 的服务端契约是什么？ |

错误、取消和资源所有权的事实统一定义在相关架构与参考专题中；指南负责应用这些事实。不能把 TypeScript 类型检查解释为运行时校验，不能把客户端实现解释为服务端承诺。

架构图至少覆盖包依赖、请求生命周期、React/Viewer 的数据与状态所有权。避免为简单线性步骤增加装饰图。保留既有 Mermaid 缩放、展开、键盘和主题行为。

## 7. API 参考的深度与层次

继续按包复杂度拆分目录，但将入口、行为契约和完整符号清单分开：

- `reference/<package>/index.md`：用途、完整安装前提、核心使用方式、主要入口选择和专题导航。不再附带数百行字母序符号表。
- `reference/<package>/<topic>.md`：围绕相关 API 家族说明选择方式、输入、默认值、结果、错误与生命周期。类型复杂时解释字段与约束；不能只复制声明后附源码链接。
- `reference/<package>/symbols.md`：完整公开符号到专题锚点的查阅索引，供搜索和已知名称的读者使用。类型、常量与辅助函数也必须有归属。

复杂包应在专题开始明确相关入口的区别。例如先解释 View、Viewer、FetcherViewer 的选择和所有权，再呈现 props/ref 契约。简单包保持紧凑，不为一行别名另建页面。

公开契约以 package.json exports、根入口递归导出及其实现为准。手写行为说明与符号索引使用同一份核对结果。保留现有测试对表格联合类型、双语页面和 LLM 描述的保护。

源码链接是进一步调查的入口，不是遗漏参数说明、依赖安装或行为解释的替代品。Agent Skill 参考也不替代面向人的开发文档。

## 8. 示例与验证来源

维护三类完整样例：

| 样例   | 可观察结果                                               | 实现约束                                                        |
| ------ | -------------------------------------------------------- | --------------------------------------------------------------- |
| HTTP   | 一次类型化请求得到固定用户结果，失败分支可复现           | 使用现有 TypeScript 编译器和 Node 本地服务夹具，无外部网络要求  |
| React  | 用户点击或修改查询后看到加载、结果、错误与取消状态       | 复用当前 React/Storybook 环境，展示真实 Hook 调用               |
| Viewer | 显示数据行列，分页/排序/过滤影响结果，保存视图有明确归属 | 复用现有 Viewer 和确定性 Storybook 数据，先本地闭环再讲后端适配 |

HTTP 样例置于 `wiki/examples/http/`，React/Viewer 样例放在现有 Storybook 能发现的文档示例目录中，不新增 workspace 包。示例目录保存可验证源文件，说明页面引用对应内容和运行路径；LLM 输出必须展开实际示例，不留下无法阅读的引用指令。

实现计划应先检查现有样例和 fixture，复用能满足上述结果的部分。新手教程提供脱离仓库使用时的必要命令与文件内容，不能只给维护者专用运行命令。

## 9. 导航与阅读体验

- 同名导航入口始终指向同一概览页；由概览选择任务。
- 每个指南组的上一篇/下一篇按任务顺序配置，API 专题按相关概念配置。包末尾提供相关指南或包概览，不自动进入另一个无关包。
- 参考侧栏先显示当前包专题，完整符号索引位于末尾；其他包通过紧凑入口切换。
- 搜索保留现有 VitePress 本地搜索。标题与描述使用用户任务和准确 API 名称，不引入新的搜索平台。
- 全站统一段落、代码、属性表和示例的展示方式。长代码与表格局部滚动，页面本身不横向溢出。
- 深浅主题下正文与链接达到普通文本 4.5:1 的最低对比目标，保留清晰焦点样式。不能仅依赖颜色表达当前项。
- 中文完整翻译标题、描述、导航和说明，API 标识符不翻译。不同语言的对应页面具有相同内容职责。

此阶段确定阅读要求，不生成视觉稿或改动主题。若后续布局选择需要视觉比较，再单独提供对比图。

## 10. 构建与维护边界

Markdown 与示例源文件为内容来源；导航使用明确的当前页面清单。现有 LLM 生成器同步覆盖开始使用、指南、架构、参考、示例与资源内容，缺失任一语言页面时失败。

LLM 文件、sitemap 与构建输出由命令生成，禁止手改。可复用当前 Reference 清单，但不扩建通用内容管理框架。只有发现具体且重复的维护问题才增加共享配置。

依赖、Node/pnpm 要求与包版本在实施时从当前 main 的清单读取。发布部署独立授权，不属于本次设计。

## 11. 验收

1. 按首次使用教程，从准备环境到执行命令可得到文档写明的结果；不能依赖未交代的路由、文件或服务。
2. React 和 Viewer 示例可在本地确定性运行；加载、失败、取消、分页与过滤的操作结果符合说明。
3. 架构页能回答依赖方向、运行环境、状态/资源所有权和失败边界，所有能力声明有源码或运行证据。
4. 全部公开 API 有可定位的契约，包入口不再堆叠完整符号表；复杂专题提供解释与选择依据。
5. 双语页面、代码与导航对应；当前链接、站内搜索和 LLM 页面集合正确，不保留旧站兼容内容。
6. 真实浏览器检查首页、首次接入、架构入口、复杂参考页、搜索、语言切换和 Mermaid；覆盖桌面与 390px 手机宽度、深浅主题和键盘操作。
7. 完成站点构建、现有文档测试、必要的示例运行验证和 diff 检查。提交前按仓库规则通过 pnpm test:unit；区分构建成功、行为验证和可用性判断。

## 12. 实施顺序

先建立当前内容到新职责的映射与阅读清单，再完成 HTTP、React、Viewer 三条样例闭环；据此编写开始使用、指南和架构页。随后整理全部包参考的入口/专题/符号索引，最后统一导航、样式、搜索和生成输出，并进行完整验收。

这是一项完整站点交付，不能以三个样例或目录骨架作为完成。实现工作在本稿获审阅确认后进入 writing-plans；不提前修改站点。

## 设计自审

- 已区分两类读者、四类主要内容及其共享事实来源，避免同一长例子跨页复制。
- 保留按包复杂度拆分的要求，同时让完整符号清单退出主要学习路径。

- 示例、内容、导航和验收均有具体完成标准；未将样例数量或符号覆盖率当作使用体验证明。
