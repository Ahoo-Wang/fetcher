# 分析视图架构与代码质量复审

审查基线：ed6c14cc。范围：此前已确认的 17 条 connector 意见、环形图 CI 失败、会话状态推导、查询编排、校验与 React 编辑器边界。以下把已复现的缺陷与结构性风险分开；不是对全仓代码做无遗漏保证。

## 结论

现状不能仅凭高覆盖率称为成熟的生产级架构。公开核心与 UI 的分离、宿主接口、编译与结果投影的职责是有价值的；但内部状态规则跨多个模块维护，类型约束和行为测试未完全承接这些规则。职责清晰度、高内聚和低耦合只做到了部分层次，尤其是编辑与查询生命周期还需收敛。

多轮审查能发现问题，本身不是质量差的充分证据；但问题反复集中在“同一状态经过不同入口后是否仍成立”，并且修复一个生命周期行为会暴露相邻测试的隐含假设，说明本项目有结构性不足，不能归因于审查工具挑剔。我此前依据局部通过和测试数量作出生产级判断过早。

## CI 根因与本次修复

环形图测试在切换前保存了 `within(legendElement)`，切换展示配置后继续使用它。`AnalysisView.tsx:735` 的 ChartBoundary key 包含完整展示配置；改变 donut 会重建图表子树。旧图例内容仍可被查询，但已不在文档中，故 toBeVisible 失败。

复现实验先增加“环形已关闭”的等待，保留旧图例断言，即在本地稳定复现脱离 DOM。修复后先等待状态切换，再从当前文档重新查询图例并验证占比，保留查询次数为 1 的断言。没有扩大超时、增加测试重试或删除占比验证。

同文件另一个键盘场景连续按两次 Escape，未等待内层 Popover 恢复焦点，曾导致外层关闭断言失败。现先等待焦点回到内层触发器，再关闭外层并等待其触发器获得焦点。16 个图表故事通过。该问题属于测试与 UI 生命周期耦合，不是聚合结果或计算错误。

## 结构性发现

### 1. 编辑有效性有多个维护者，缺少统一的生命周期契约（高优先级）

证据：`AnalysisView.tsx:70-97` 在 React 中维护根条件和范围条件有效性；`ViewEngine.ts:308` 接收一个布尔值；`sessionState.ts:111-165` 推导会话校验；`ViewReload.ts:73-96` 采纳远端时又必须显式保留有效性。此前 reload、restore、useRemote 分别遗漏同一类未提交编辑缓冲问题。

核心允许扩展持有本地草稿是合理的，问题是一个布尔值不足以描述“哪个实例、哪个编辑器生命周期、哪些未提交输入”对当前命令的约束。不能简单把所有草稿迁进引擎，也不能在还原/重载时凭空设为有效。

建议：先定义实例编辑生命周期的动作表，统一管理保留/重置语义与有效性登记。UI 持有输入文本，引擎持有当前编辑生命周期的提交阻塞信息；采纳远端、还原和切换都走同一组明确转换。是否需要版本标记应由迟到回调回归决定，不先增加通用事件框架。

### 2. 校验结果的所有权跨越推导和存储层（高优先级）

证据：`sessionState.ts:149-163` 生成筛选、编译和展示问题；`SessionStore.ts:79-130` 在 publish 中追加配置大小问题，并为了缓存快速路径专门恢复旧错误。此前同一配置引用下有效性变化曾丢失 config-size。

命令执行和宿主写入边界再次验证是必要的防御，不能删掉；但最终用于 UI 和命令资格判断的校验结果，应有一个明确的推导入口。当前扁平列表还通过 `ViewQueries.ts:69` 的 `id !== 'presentation'` 编码“什么错误阻止查询”，策略与显示消息分类相互依赖。

建议：统一推导配置、编辑、资源和展示约束；由显式策略计算 canRun/canSave。Store 负责不可变发布与缓存管理，避免在通用 publish 中悄悄修补业务校验。保留真正的信任边界检查，而非机械追求只校验一次。

### 3. 查询触发策略分散，造成时序耦合（高优先级）

证据：`ViewQueries.ts:35-75` 同时维护 opened、取消后的清理、selection/generation 和 refresh 特例；`AnalysisCommands.ts:107-196` 拥有在途请求与执行校验；`AnalysisView.tsx:326-348` 又在 UI 中重新编译并决定自动刷新资格。此前显式 reload 不刷新和取消首次查询后无法重访，是同一生命周期的不同缺口。

多个保护令牌并非天然错误：导航、销毁、请求替换确有不同身份。问题在于触发原因仍由布尔参数和入口特例隐式表达，同一规则必须在多个位置被记住。

建议：先集中“首次打开、显式重载、自动刷新、手动运行”是否执行的纯策略，输入为明确意图和会话状态；UI 只表达意图，执行器拥有请求、取消和迟到结果处理。以动作序列测试验证策略，不先新增一套调度框架。

### 4. 内部 patch 类型弱于公开会话契约（中优先级）

证据：`SessionStore.ts:35-46` 将记录与分析字段合并为宽泛 Partial，`SessionStore.ts:200` 再断言为 ViewSession。外部有判别联合，内部却允许调用者拼出跨种类字段组合，需要运行时与测试补救。

这是类型设计风险，不代表已经证明某个公开调用可产生非法会话。建议按记录/分析保留判别关系，或为关键状态转换提供类型收窄的函数；避免把所有字段都变成可选更新项后再强制断言。

### 5. UI 内聚度不足，组件承担过多变化原因（中优先级）

证据：AnalysisView 804 行，既管理响应式 Portal 容器、全屏、自动刷新，又推导执行资格、结果状态和表格排序操作；AnalysisEditor 912 行集中处理不同组件类型的表单和更新规则。行数不是判定依据，关键是修改查询策略、弹层生命周期、展示配置都需要进入相同组件。

建议按现有稳定职责提取工作区布局、编辑器生命周期和结果展示；查询业务规则移回引擎。不要只把大文件拆成小文件而继续共享全部状态，也不要为每个控件创建通用插件层。

### 6. 测试覆盖了许多分支，但状态转换覆盖仍不系统（中优先级）

此次环形图 CI 表明，旧测试甚至可能在新状态提交之前“成功”。高覆盖率证明代码被执行，不证明每个公开动作的前置条件、后置条件、取消/冲突组合均正确。此前补丁回归大多按单条评论补齐，缺少从规则出发的统一验收表。

建议保留单元与浏览器测试，同时补足有限的关键序列：输入无效→还原/重载/采纳远端；首次查询→切换→取消→返回；成功结果→编辑→保存→刷新；图表配置改变→异常恢复→数据表切换。异步交互测试每一步等待可观察后置条件，变化后重新定位 DOM。避免依赖固定 sleep、重试直到偶然通过或仅检查按钮存在。

## 应保留的架构基础

- `test/architecture.test.ts:30-55` 实际检查公开核心无 React/浏览器依赖以及运行时导入图无环；这比目录命名更有说服力。
- ViewHost 对数据源和实例持久化的接口隔离、编译器与结果投影的分离，有明确用途，无需推倒重建。
- 配置与已执行结果分离、不可变快照及请求取消令牌是必要约束，应由统一规则强化，而不是为了少代码删掉。
- 当前扩展原型键问题已经有针对性修复；它属于边界编码缺陷，不足以单独否定整套插件架构。

## 收敛顺序与交付标准

1. 完成本次确定性的 CI 等待修复，保持既定性能与覆盖率门槛。
2. 写清编辑状态与查询动作的不变量，集中转换/资格策略；优先消除多处维护同一布尔状态的规则。
3. 收窄内部 patch 类型和最终校验推导职责；以已有失败回归保护迁移。
4. 最后按职责缩小 UI 组件，使布局变化无需修改引擎规则，新增查询入口无需复制资格判断。

不建议继续扩展功能或单纯堆测试数量，也不建议在本次 CI 修复中顺手全面重写。生产交付应以状态转换回归、最新提交的完整 CI/浏览器验收、宿主契约验证为证据；不能承诺审查不再发现问题。

需要进一步明确的产品语义：用户选择“使用最新版本”通常意味着放弃本地编辑；当前保留无效标记是阻止错误执行的保守修复，还不能代替“所有相关编辑器同时丢弃本地缓冲并进入新编辑生命周期”的完整约定。应把这项语义与“还原”“重载但保留本地修改”区分，而不是让每个入口自行猜测布尔值。
