# View Engine 方案收敛审查

日期：2026-09-10。范围：无兼容约束的统一重设计，侧重第一性原理、职责分层、维护性与 UI/UX。仅评审，不修改当前规格或生产代码，不新增运行验证。

## 1. 总体结论

方向合理，可以进入具体契约与交互原型的验证，不应再围绕同一问题不断增加新层、状态框架或整份重写。但在完整实施前需要收口两项高优先级契约：记录/分析的保存语义，以及每实例的原子状态提交。UI 的重点是降低状态理解成本。

第一性原理：定义说明可以做什么；实例保存用户意图；编辑会话承载暂未完成的意图；查询结果是执行某份意图后取得的观察；页面只是让用户访问这些能力。领域区别来自记录处理与聚合分析，不来自它们是否放在同一侧栏。

## 2. 应保留的设计

| 设计                                    | 理由                                                             |
| --------------------------------------- | ---------------------------------------------------------------- |
| 单一 ViewEngine，类型专属会话/命令      | 实例管理共享，业务操作按真实变化原因隔离                         |
| 一套定义和判别联合实例，无兼容分支      | 尚未发布，维护双格式/双入口没有收益                              |
| saved / working / result                | 分别对应持久化事实、编辑事实、观察事实，保存与查询失败可独立解释 |
| 加载生命周期与配置有效性分开            | 输入无效仍可编辑，修复草稿不会因状态切换失去所有者               |
| 集中处理 revision、requestId 和未知结果 | 同一正确性要求只实现一次                                         |
| 组件配置与纯编译成对注册                | 保存/恢复与运行来自同一协议，避免 UI 和手写查询漂移              |
| 分析结果身份与记录身份分开              | 聚合组不是业务实体，不能复用业务 rowKey 或批量操作               |

不应为了形式上的四层，每层再拆一套 manager/service/repository。现有宿主端口、纯函数、领域会话和一个状态发布位置已能承载这些职责。

## 3. P1：同名保存操作应具有一致语义

当前重设计明确分析可直接保存有效 working，但将简化状态定义为“分析会话”，记录仍保留现有查询行为。当前实现的共享 ViewPersistence 在 filterPending 时拒绝保存（`packages/view-engine/src/record/engine/ViewPersistence.ts:68`）。如果重构只是照搬该约束，分析将被记录状态限制；若只给 analysis 特判，公共“保存”又出现两套含义。

用户反例：在分析实例修改筛选后直接保存成功，切到记录实例做同样的修改却被要求先查询。在没有兼容性要求的前提下，这种差异缺乏业务依据。

建议：统一所有实例的保存含义为“校验并保存当前工作配置”，不要求先执行。记录是否在分页、切换或特定交互时重新查询，仍由记录会话决定；共享持久化只接受类型模块生成的有效、不可变保存候选，不读取 filterPending、page 或 metrics。

记录也必须区分 working 与实际展示结果对应的查询范围，业务操作继续绑定真实已查询范围，不能因保存了新筛选就把旧 rows 解释为新结果。统一的是保存语义与事实边界，不要求两类结果结构相同。

本项是规格收口建议，不声称“记录当前禁止未应用筛选保存”本身就是旧实现缺陷。用户已经解除兼容约束，现有行为不应自动变成新设计必须保留的需求。

## 4. P1：领域所有权与状态写入权需要区分

规格称 saved 由共享持久化拥有，working/result 由分析会话拥有。这个职责划分合理，但不能据此建立独立可写存储，再靠订阅互相同步。

反例：保存响应先更新 saved，稍后才清除 writeAttempt；或恢复服务器配置先更新 working，稍后才更新 revision。中间状态会被 UI、订阅回调或下一条命令读取，产生错误 dirty、重复提交或恢复判断。已有工程包含同步订阅重入测试，这不是可以忽略的假设。

建议：每实例只有一个权威快照与一次原子提交入口。领域模块拥有状态变化规则，持久化拥有服务协议，最终都由应用层把已核验的更新原子提交；保存完成时 saved、写入过程及冲突标记一次发布。原子提交后的订阅通知不能再修改这次提交的归属。

一个工作区 Store 可以容纳这些每实例快照，不意味着每实例都需要新建 Store 类。可以继续使用现有不可变发布机制；禁止两份可变状态镜像和 UI 直接写 Store。类型模块可返回状态变更结果，具体实现不需要通用事件总线或大型 reducer 框架。

实施前用保存中继续编辑、通知回调立即重试、A→B→A、重载与查询交错四条时序证明这一边界。

## 5. P2：状态应按用户任务分区呈现

saved/working/result 是内部事实，不宜直接变成三个大面板或一排状态徽章。状态同时存在是正确性要求，用户同时阅读所有状态不是。

| 页面位置     | 只表达本区域的问题         | 例子                                           |
| ------------ | -------------------------- | ---------------------------------------------- |
| 头部保存操作 | 持久化状态                 | 未保存、保存中、保存失败、需处理冲突           |
| 配置区       | 输入及当前编辑有效性       | 请选择日期粒度；当前排序及清除入口             |
| 结果区       | 数据属于哪次请求及能否更新 | 结果接收时间、配置已改变、运行中或本次查询失败 |
| 实例导航     | 非当前实例需要注意的状态   | 未保存标记、保存失败/待核对                    |

失败反馈就地给出下一步，不统一抛到全页错误条。结果陈旧提示与接收时间合并成紧凑摘要；设备时间来源及相对时间规则放在可访问的说明中，正常流程不占据大段警告区域。当前实例头部已展示保存状态时，导航无需重复堆满同样文字。

主操作固定叫“运行分析”，失败且当前配置未变时结果区可给“重试”；避免主按钮频繁变成多种近义名称。保存与运行独立，但位置稳定、反馈归属明确。只读用户可进行定义允许的临时分析，标记“临时修改”并有恢复入口，不催促执行没有权限的保存。

## 6. P2：首次进入与回访策略应成为显式默认值

当前“首次可自动运行、回访手动运行”可以成立，但“可”不能留给各组件自行决定。建议固定默认：首次打开有效已保存分析实例执行一次；同一引擎内回访恢复快照，不自动运行工作内容；取消/失败后不循环自动重试。记录自动查询策略由其任务需要明确规定。

首次、回访与页面刷新不是三套配置：访问历史属于会话运行状态，刷新页面创建新会话后属于首次进入。用户保存但未运行的配置在同一会话回访时不运行，新开页面后可按首次规则执行；UI/文档要说清楚这个边界。

无需因此新增自动查询配置矩阵、TTL、后台调度器。未来如果有真实嵌入场景要求手动首查，再增加单一有明确语义的选项。

## 7. UI/UX 最小闭环

用户从系统分析模板进入，看到有效默认指标和结果；按需展开配置，修改维度/指标；可运行查看，也可直接保存配置。任何失败都保留可恢复输入，并给本地修复或远端核对入口。

配置区只包含筛选、维度、指标、排序/上限。表格列宽/显示顺序属于展示设置，不混入统计指标编辑。指标命名、函数和字段同时可见，使“销售额 = 金额求和”可被理解；不用别名或注册名称代替业务标签。

混合导航沿用个人/公共分组，实例类型用文字和图标表示，不新增模式切换。独立 RecordView/AnalysisView 可以脱离导航使用。窄屏收起侧栏、配置纵向排列、结果表局部滚动；异步返回不抢键盘焦点。

首版无图表和下钻是已确认边界，不应在每次审查中重新列为产品缺陷。没有真实画面和浏览器操作证据，本轮不能评价具体视觉密度、对齐、对比度或焦点体验已经合格。

## 8. 进入实施的最小输入

只需要补齐三份具体材料，不需要再增加一轮泛化架构：

1. 一组公开调用样例：记录、纯分析、混合页面，包含身份、生命周期、类型命令与失败入口。
2. 一张命令/状态表：编辑、保存、运行、恢复、另存、冲突核对分别读取和修改哪些事实，哪些组合互斥，哪些更新原子发布。
3. 一个可交互的代表性流程：修改未运行 → 直接保存 → 运行失败 → 修复排序 → 切换返回 → 冲突处理；桌面和窄屏各检查一次。

上述是下一阶段验证材料，不表示本次已经创建原型或运行测试。当前不再需要兼容层、额外引擎入口、通用插件生命周期、通用合并编辑器或新的状态管理依赖。

判定：概念架构通过方向审查；公共契约和原子状态更新尚需具体验证；UI 信息结构合理，视觉与实际交互未验收。历史已复现的输入丢失、冲突回退与整体加载失败仍需在实现阶段修复，不能因规格改写而视为完成。
